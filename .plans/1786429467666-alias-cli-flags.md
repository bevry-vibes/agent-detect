# Alias / case-variation resolution for `--harness=`/`--provider=`/`--model=` CLI flags

## Goal

Accept aliases, capitalisation changes, spaces, and display-name variations for
the harness / provider / model given via CLI flags, so e.g. all of
`--harness=kilo`, `--harness=kilo-code`, `--harness='Kilo Code'`,
`--harness='Kilo Code CLI'` (and `--harness=KILO`) resolve to the canonical
`kilo` rule. An alias must never be ambiguous — e.g. in cline both `cline` and
`cline-pass` are providers, and `cline` must resolve to `cline` only.

## Current behavior (verified)

`cooked`/`trailer`/`check-reciprocal` route `--harness=--provider=--model=`
through `resolveRecipe` (src/main.zig:2710). Matching is `ruleIdMatches`
(src/main.zig:930): exact canonical name OR the strict slug of the canonical
name. The input is **not** lowercased or stripped, so today:
- `kilo` resolves; `kilo-code`, `Kilo Code`, `Kilo Code CLI`, `KILO` all fail.
- `cline` resolves; `clinepass`/`cline-pass` resolve to `cline-pass`;
  `Cline Pass` (the label) fails.
- `fixtures queue`/`dequeue` dim filters store `--harness=` etc. raw and compare
  raw against store rows (so `--harness=kimicode` fails to match rows whose
  `harness` column is `kimi-code`).

The "top 50" alias handling is only a **documented convention**
(CONTRIBUTING.md: name variations coalesce to one canonical model); there is no
code-level alias table to reuse. This feature introduces the code-level
`variations` field following that same convention.

## Design decisions (resolved)

1. **Scope**: recipe-mode flags (`cooked`/`trailer`/`check-reciprocal`) AND
   `fixtures queue`/`dequeue` dim filters (and the h/p/m parts of
   `--agent=`/`--fixture=`). Known aliases canonicalize; unknown strings pass
   through raw in the fixtures seed path (seeds intentionally allow unknown
   ids). `--platform=` gets no alias resolution.
2. **Match surfaces**: each rule's alias set = canonical `name` + `label` +
   `short_title` (if present) + explicit `variations` (new field), all
   normalized via the slug rule (lowercase + strip non-alphanumeric). Exact
   canonical-name match takes precedence. So `Kilo Code` works via the label
   with no data entry; only `Kilo Code CLI` needs a `variations` entry.
   Normalization is **whole-string** — no word stripping (stripping `-code`/
   `cli`/`pass` would wrongly conflate `kimi-code`↔`kimi` and `cline-pass`↔
   `cline`).
3. **Conflict guard**: a `zig build test` assertion builds the full normalized
   alias set per table and fails if any alias slug maps to more than one rule.
   The resolver stays deterministic (first rule in array order wins) so a
   slipped-through conflict cannot crash.

## Implementation steps

1. **Normalizer**: reuse `slugId` (src/main.zig:1021 — lowercase + strip
   non-alphanumeric) as the canonical normalization for both rule aliases and
   CLI input. Add a file-level `pub fn canonicalIdFor(a, comptime Rules: type,
   rules: []const Rules, input: []const u8) ?[]const u8` that:
   - returns the rule whose canonical `name` equals `input` (exact, unchanged
     fast path), else
   - normalizes `input` via `slugId` and returns the first rule whose normalized
     alias set (name, label, short_title, variations) contains it, else null.

2. **Add `variations` field** (default `&.{}`) to the three rule structs:
   - `HarnessRule` (src/main.zig:601)
   - `ProviderRule` (src/main.zig:353) — also add `short_title: ?[]const u8 =
     null` (currently absent; keeps the generic resolver simple)
   - `ModelRule` (src/main.zig:132)

3. **Starter variations data**: add `variations` only where a common alias is
   not already covered by name/label/short_title, e.g. harness `kilo` →
   `variations = &.{ "Kilo Code CLI" }`. Enumerate a small starter set for the
   rules that have a well-known extra alias; rely on label/short_title matching
   for the rest. Document the convention (see step 7) so future rules add
   variations only when needed.

4. **Wire the resolver into `resolveRecipe`** (src/main.zig:2710): replace the
   `harnessRuleForName`/`providerMetaForName` + `ruleIdMatches` loops with
   `canonicalIdFor` over the three tables; keep `return null` → exit 7 for
   unknown combos. Also make `canonicalHarnessName`/`canonicalProviderName`/
   `canonicalModelName` (src/main.zig:3910-3931, used by `comboDims` for
   build*Env) thin wrappers over `canonicalIdFor` for consistency.

5. **Wire into `parseFilters`** (src/main.zig:4693+): after the parse loop,
   canonicalize `f.harness`/`f.provider`/`f.model` when they resolve to a known
   rule; leave the raw string otherwise (seed path). Canonicalize the h/p/m
   parts of `--agent=`/`--fixture=` after `splitAgentId`/`splitFixtureId`;
   leave the platform part raw. This also fixes `fixtures queue --harness=
   kimicode` (slug form) matching `kimi-code` store rows.

6. **Uniqueness test**: in `src/exit_statuses.test.zig`, iterate
   `rulesForHarnesses` / `rulesForProviders` / `rulesForModels`, build each
   rule's normalized alias set, and assert no alias slug maps to two different
   rules within the same table (e.g. `cline` vs `cline-pass` stay distinct;
   the test must fail if a future `clinepass`-colliding variation is added).
   Also assert each rule's own alias set is internally non-duplicated.

7. **Resolver tests** (same file):
   - harness: `kilo`, `kilo-code`, `Kilo Code`, `Kilo Code CLI`, `KILO`,
     `kilocode` all resolve to `kilo`.
   - provider: `cline` → `cline`; `clinepass`, `cline-pass`, `Cline Pass`,
     `CLINE_PASS` → `cline-pass` (never `cline`).
   - model: `minimax-m3`, `MiniMax M3`, `minimaxm3`, `M3` → `minimax-m3`;
     `deepseek-v4-flash` and `deepseek-v4-flash-free` stay distinct.

8. **Docs**: CONTRIBUTING.md "add a new model/provider/harness rule" — document
   the `variations` field, the normalization rule (lowercase + strip
   non-alphanumeric, whole-string, exact-name precedence), and the uniqueness
   convention. Note the alias acceptance in the cooked/trailer recipe-mode
   description.

9. **CI smoke asserts**: extend the three `smoke asserts` blocks in
   `.github/workflows/build.yml` with one alias-form invocation, e.g.
   `check-reciprocal --harness='Kilo Code' --provider='Cline Pass'
   --model='DeepSeek V4 Flash'` must equal the canonical-form result
   (`--harness=kilo --provider=clinepass --model=deepseekv4flash`).

- Manual: re-run the gap checks from this plan — all four kilo forms and

  `--trailer "$(./zig-out/bin/agent-detect trailer co-author)"`.

## Risks / edge cases

- **Ambiguity**: prevented by the uniqueness test; resolver is
  deterministic-first-rule otherwise.
- **Seed path**: fixtures commands keep unknown raw strings (e.g.
  `--harness=devin` for a not-yet-listed harness) so seeds still work.
- **Empty/whitespace-only input**: normalized to empty → no match → exit 7
  (recipe mode) / raw pass-through (fixtures).
- **Non-ASCII**: `slugId` strips non-ASCII alphanumerics (std.ascii) — inputs
  with non-ASCII chars simply won't match.

## Out of scope

- Live-detection `applyModel`/`applyProvider` family fallbacks (not CLI).
- `--platform=` alias handling.
- Enumerating an exhaustive per-rule variations list (starter set only; the
  mechanism + convention is the deliverable).

**Key code facts**:
- `StdIo` union (`std/process.zig` ~408): `inherit` / `file: File` (pass an already-open file) / `ignore` / `pipe` / `close`. `Dir.createFile(dir, io, path, CreateFileOptions)` with `{ .read = bool, .truncate = bool (default true), .exclusive = bool }`.
- `std.Io.File` has a **private** `handle: Handle` field — you cannot get the raw fd/handle out of a `std.Io.File`, which is why poll-on-pipe approaches were abandoned.
- **`std.posix.poll` / `POLLIN` / `pollfd` compile on this Windows target but `std.posix.pipe` does not exist** (and `fd_t`/`pollfd` are `void` on some non-libc paths) — do NOT build a poll-based design on `std.posix` here.
- `readChildOutput(a, io, child, comptime stderr: bool)` exists in core.zig (line 1585) — reads until EOF, 64KB cap for stderr. The daemon no longer uses it for the worker (uses inline streaming now).

## Strategy: why this design (for the visibility feature)

- A naive "tee worker stdout" needs to **drain** stdout or the worker deadlocks on a full pipe. Polling two pipes (or one) was blocked because `std.Io.File` doesn't expose its handle and `std.posix.poll` is unreliable here.
- The adopted design sidesteps all of that: **one** pipe (stdout) drained by the existing streaming reader + **one** file (stderr). One pipe can't deadlock the single reader; the file can't block; the child's real exit code is preserved (no shell wrapper needed); and the failure record gets both streams.
- **One daemon per host** (rule added to runbook): a second daemon double-drains the queue and interleaves the same `daemon.log`. A hung daemon doesn't answer `daemon.ctl` — kill by the banner pid and kill orphaned `fixtures capture` workers.

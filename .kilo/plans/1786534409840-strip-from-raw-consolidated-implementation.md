## Goal

Remove `from-raw` end-to-end and land the decided replacement
architecture: two modes (queue defaults to enqueueing **both** —
a from-identity row and a from-capture row per candidate; exactly one
mode when exactly one `--from-*` flag is given; both flags together are
rejected, since combining filters ANDs), committed SQLite store with
platform-aware popping,
`available`+`successful` persisted on both tables with pure-enqueue
queue flags, per-channel generation columns replacing `origin`, no
mechanical evidence checks, the `pending`-table seed protocol under a
pure daemon, the `invalid` table, the `--missing-fixture` split,
table-based `--stale-by-detect`, the fixture envelope reshaped into
per-channel keys (`from-identity` / `from-capture` / `from-capture-raw`,
root `trailer` dropped), and both-channel regeneration of the fixture
matrix with zero file deletions.

Hard rules (user-decided, non-negotiable):

1. **No synthetic-state testing anywhere** — no new detect()/env/HOME
   fabrication tests, no replacement for A's `detect_ladder.test.zig`.
2. **Queue/dequeue never evaluate** — they only add/remove rows
   (`--missing-fixture-entry`'s fixtures-entry insert and invalid-table
   routing are the sole sanctioned non-queue writes; they do no
   evaluation). Only the daemon probes/captures.
3. **No fixture-file deletions** — regeneration replaces files in place
   (atomic temp-write + rename on success); failed attempts leave the
   previous committed file untouched.
4. **reasonix is available on this Windows host** — only
   `reasonix-deepseekflash-deepseekv4flash` has a launch spec; the other
   two reasonix recipes are no-launch (→ `invalid` under from-capture,
   queueable under explicit `--from-identity`).

## Fixture file shape (reshaped outputs — amends 2+3+4)

The `cooked` envelope key splits into per-channel keys, each defined as
a real subcommand output (verified 2026-08-12: the released `identify`
action serializes `buildCooked` — with `--harness/--provider/--model`
(all three) it resolves via `resolveRecipe`, zero-token, no detection
(~6917); `agent-detect-dev raw` serializes `buildRaw` (~3307); the
`trailer <subtype>` action accepts the same complete-combo flags for
recipe-mode output (~6774-6782) and builds via `buildTrailerLine`
(~6945-6950)):

```json
{
  "from-identity": {
    "identify": { …agent-detect identify --harness=H --provider=P --model=M output… },
    "trailer co-author": "…agent-detect trailer co-author --harness=H --provider=P --model=M output…",
    "trailer assisted-by": "…agent-detect trailer assisted-by --harness=H --provider=P --model=M output…"
  },
  "from-capture": {
    "identify": { …agent-detect identify output, run inside the captured session… },
    "trailer co-author": "…agent-detect trailer co-author output, run inside the captured session…",
    "trailer assisted-by": "…agent-detect trailer assisted-by output, run inside the captured session…"
  },
  "from-capture-raw": { …agent-detect-dev raw output, run inside the captured session… }
}
```

(Each trailer value is the spawned command's stdout, trimmed — a
single-line string.)

- **No root `trailer`, and no `trailer` field inside `identify`
  either** (amend 4): `buildCooked` drops its `trailer` field
  (~2596) — 18 → 17 canonical fields — so the released `identify`
  output no longer carries it. Each channel's `"trailer co-author"` /
  `"trailer assisted-by"` values are generated by **spawning the real
  CLI** and recording stdout: `agent-detect trailer co-author` /
  `agent-detect trailer assisted-by` — with the complete-combo flags
  (`--harness=H --provider=P --model=M`) for from-identity, bare
  (session-env detection) for from-capture. Workers spawn the current
  executable (the dev binary during daemon runs; same action surface);
  `buildTrailer`/`buildTrailerLine` stay as the action's internals.
  Persisting **both** variants per channel fixes the historical gap
  that trailer variations were never exercised. (Followup 2's
  from-capture example wrote `"trailer attributed-by"` — confirmed a
  typo for `assisted-by` in followup 4; the only subtypes in the code
  are `co-author` / `assisted-by` (~6784, ~6947).)
- **`from-capture-raw` is top-level, not nested** under `from-capture`:
  `from-capture` is released-binary (`agent-detect`) output, whereas
  `from-capture-raw` is dev-binary (`agent-detect-dev raw`) output.
- **Channel ownership:** an identity job writes `from-identity` only
  (a locally-computed raw block would describe the _generation host's_
  environment, not the combo's — misleading; provenance now lives in
  the table's generation columns). A capture job writes `from-capture`
    - `from-capture-raw` and leaves any existing `from-identity`
      untouched.
- **Merge semantics:** the worker loads the existing file if present,
  replaces only its own channel's keys, and writes back atomically
  (temp + rename). Declared-only fixture = `{ "from-identity": … }`;
  captured fixture = all three top-level keys. A missing
  `from-capture`/`from-capture-raw` key is the in-file mirror of a NULL
  `capture_generation_*` column.
- Internal builder names (`buildCooked`, `buildRaw`, `Detection`,
  `buildTrailerLine`) stay — only the envelope keys change; docs stop
  saying "cooked".
- Legacy `cooked`/`raw`/`origin`/`trailer`-shaped committed files are
  replaced by regeneration (never deleted); `--missing-fixture-entry`
  derives ids from the filename + recipe table, so it never sniffs the
  old shape.
- Reshaping the `identify`/`raw` outputs themselves is in scope if the
  envelope needs it (user: "this involves reshaping the outputs, which
  is fine").

### 3. Two-mode surface — both by default (amend 6)

- Mode parse (~4850): only `--from-identity` / `--from-capture`.
  **No flag → the queue command enqueues one row per selected mode per
  candidate: a from-identity row AND a from-capture row** (identity
  inserted first). Exactly one flag → that mode only. Both flags →
  exit 3 (AND semantics make the combination empty; reject explicitly).
  There is no default stamp: every queue row is stamped explicitly, so
  the schema's `mode` default is dropped (column stays NOT NULL) and
  `QueueRow.mode` (~3444) loses its default value.
- `queue_dedupe` gains `mode` — otherwise the both-default's second
  insert would `INSERT OR REPLACE` the first for the same candidate.
- Pop ORDER BY / DELETE CASE (~3682, 3695), `modeRank` (~5848-5852):
  two-way — `from-identity` (0) < `from-capture` (1); with both rows
  queued, a combo's declared file lands before its capture upgrades it.
- `dequeue`: no mode flag still filters all modes (unchanged);
  `--from-identity`/`--from-capture` remain dequeue filters.
- Supersedes the earlier "default mode = from-capture" decision (both
  compared plans + the register's shared-ground note).

### 5. Queue scopes — pure enqueue only

`parseFilters`/`scopeCandidates` (~4840-5100) rewritten so **every**
scope only INSERTs queue rows (plus the two sanctioned exceptions
below); delete all probe stamps (~5042-5044, ~5094-5097):

- Recipe-universe (host platform): `--recipes`,
  `--missing-fixture-file` (recipe has no `fixtures/<id>-<host>.json`).
- Fixtures-table universe (rows keep their stored platform):
  `--all`, `--stale-by-minutes`, `--stale-by-version`,
  `--stale-by-detect` (rows with NULL or ≠ `build_options.version`
  `agent_detect_version`), `--stale-by-hash` (below),
  `--available`/`--unavailable` (`fixtures.available = 1/0`),
  `--successful`/`--unsuccessful` (`fixtures.successful = 1/0`). Each
  stamps its queue marker; all compose with dim filters + mode flags.
  `--unsuccessful` is the designated catch vector for **unsuccessful
  fixtures with valid ids** (followup 9) — e.g. captures whose
  `from-capture-raw.detected` ≠ `[harness, provider, model]` (partial
  detection stamps `successful=0`). Such rows are NOT `invalid`-table
  material: their ids are valid; their last attempt failed. Only bad
  ids go to `invalid`.
- **`--partial` is removed entirely** (amend 5): flag parse (~4834),
  `FilterOptions.partial`, scope-count terms (~4881, ~4970), the
  `scopeCandidates` seed branch (~5051-5064), the `--partial` usage
  line (~3128), and every struct/DDL/prop listed in T4. Rationale:
  queue rows are either full-dim rows or NULL-dim seeds expanded into
  `pending` (always defined fixture_ids); `fixtures` rows require
  defined ids (bad ids → `invalid`); nothing partial persists, so the
  scope has no universe.
- **`--stale-by-hash`** (amend 5; `--partial`'s successor; renamed in
  amend 7): fixtures universe; a row is a candidate when, per selected
  channel, the stored generation hash IS NULL OR ≠ BLAKE3 of the
  current fixture file's channel object (missing file or missing
  channel object = stale). The mode flags constrain which hash is
  checked: `--from-identity` → `identity_generation_hash` vs the file's
  `from-identity` object; `--from-capture` → `capture_generation_hash`
  vs the file's `from-capture` object; no flag (both) → both checked,
  one row queued per stale channel's mode. Stamps `stale_by_hash=1`.
  Pure file read + hash — no evaluation. Does NOT catch recipe-table
  drift (the file and column drift together); that remains
  `--stale-by-detect` (version bump) or `--recipes`.
- **Mode-set emission (amend 6):** every scope emits one row per
  selected mode per candidate — both modes when no `--from-*` flag,
  one when exactly one flag, exit 3 when both. (For table-universe
  scopes, "both" means a from-identity row and a from-capture row for
  the same fixtures row; dedupe distinguishes them via `mode`.)
- `--missing-fixture` is **gone**; `--missing-fixture-entry` (sanctioned
  exception 1): scan `fixtures/*.json`; file with no `fixtures` row →
  valid ids (known recipe dims + filename platform): INSERT fixtures
  entry (`successful=1`, `generated_at=now`, `harness_version=NULL`,
  `available=NULL`, `agent_detect_version=NULL`, generation columns
  NULL, derived ids) — no queue row; invalid ids → `invalid` row
  (reason e.g. `unknown fixture file`); **the file persists**.
- No-launch-spec handling at queue time (sanctioned exception 2):
  from-capture candidates with no `.launch` → `invalid` row
  (reason `no launch spec`), not queued, warning printed suggesting
  `--from-identity`. Under the both-default this means a no-launch
  recipe yields its from-identity row + an `invalid` entry (the
  capture side is suppressed); under `--from-identity` alone it queues
  normally (declared generation needs no launch).

### 6. Daemon rework — purity + pending protocol + platform popping

- **Purity:** init runs `ensureSchema` only. The daemon never writes
  `fixtures` outside pop processing, never inserts queue rows, never
  backfills.
- **Pop filter:** `AND (platform IS NULL OR platform = '<host>')` on the
  SELECT and the DELETE subselect; non-host rows stay queued.
- **Uniform pending flow:** popping any queue row materializes 1..n
  `pending` rows (`INSERT OR IGNORE` — the UNIQUE(queue_id, fixture_id)
  index makes crash-resume safe): a full row → one pending row; a seed
  (NULL dims) → one per expanded recipe for the host platform
  (no-launch recipes under from-capture → `invalid`, excluded). Process
  each pending row (`started_at` on start, `finished_at` on completion,
  fixtures upsert per outcome below); when `pendingDrained(queue_id)`:
  delete the pending rows and the queue row. On startup after a crash,
  a seed whose pending rows exist resumes its unfinished rows (mode is
  read from the still-present queue row).
- **from-identity job:** `runOneComboIdentity` → success: merge-write
  the `from-identity` object — `identify` from `resolveRecipe` +
  `buildCooked` (17 fields, no trailer), `"trailer co-author"` /
  `"trailer assisted-by"` from spawning `agent-detect trailer
<subtype> --harness=H --provider=P --model=M` and recording stdout
  (temp + rename; existing `from-capture`/`from-capture-raw`
  preserved) — and upsert `successful=1`, `generated_at=now`,
  `identity_generation_at=now`, `identity_generation_hash` (over the
  `from-identity` object), `agent_detect_version=build_options.version`,
  `harness_version=NULL`; failure: upsert `successful=0`,
  `generated_at=now`.
- **from-capture job, in order:** launch-spec backstop guard (no launch
  → `invalid` row, finish; no fixtures write) → `harnessAvailable`
  probe (fail → upsert `available=0`, `successful=0`,
  `generated_at=now`, finish) → `runOneComboCapture` + post-checks
  (parse + combo-match only) → success: merge-write `from-capture`
  (`identify` from the session's live `detect()`; trailer variants from
  spawning bare `agent-detect trailer <subtype>` in the session env) +
  `from-capture-raw` (temp + rename; existing `from-identity`
  preserved), upsert `available=1`, `successful=1`,
  `capture_generation_at/hash` (hash over the `from-capture` object),
  `generated_at=now`, live `harness_version`,
  `agent_detect_version=build_options.version`; failure: upsert
  `available=1`, `successful=0`, `generated_at=now` — partial temp file
  discarded, committed file untouched. **Detection-partial counts as
  failure** (followup 9): when the session's `detect()` resolves only
  1–2 dims (`from-capture-raw.detected` ≠ the full
  `[harness, provider, model]` triple; the `fixtures capture` exit-8
  path), the worker writes no fixture file and the job takes this
  failure upsert — the combo's ids are valid, so it is retried via

## Data flow (one paragraph)

`queue` writes queue rows (pure). The daemon pops host-platform rows,
materializes jobs into `pending`, evaluates per job (probe/capture or
declared generation), stamps `fixtures`
(available/successful/version/generation columns), merge-writes only its
channel's file keys (`from-identity`, or `from-capture` +
`from-capture-raw`), and finishes pending rows; drained seeds delete
their pending + queue rows. Invalid ids from
queue time, seed expansion, or `--missing-fixture-entry` land in
`invalid` for dev-agent remedy. Everything syncs across hosts via the
committed DB + fixture files; only the matching platform's daemon pops
a row.

## Failure modes

- Capture worker timeout/nonzero/post-check fail/detection-partial
  (exit 8) → `successful=0` (`available=1` if probed), item consumed,
  no auto-retry, no spin; manual retry via `--unsuccessful` (the valid-id
  failure vector) or `--unavailable`.
- Harness unavailable at pop → `available=0, successful=0`, consumed.
- Daemon crash mid-seed → pending rows persist; next run resumes
  unfinished rows (UNIQUE dedupe prevents re-expansion duplicates).
- Partial capture write → temp file discarded; committed file intact.
- Two hosts committing the DB concurrently → binary merge conflict;
  single-writer workflow (pull before daemon, commit after).

## Risks / notes

- No auto-retry by design; transient capture failures need a manual
  `queue --unsuccessful`.
- `--stale-by-detect` fires only after a `build.zig.zon` bump (or on
  NULL versions, e.g. `--missing-fixture-entry` rows); same-version
  format churn falls back to `--recipes`.
- `--stale-by-detect` also enumerates failed rows (NULL
  `agent_detect_version`) — acceptable; dedupe keeps enqueue idempotent.
- The DB dirties on every upsert; commit when work lands.
- `runner`/`created_at` remain per-host noise by design.
